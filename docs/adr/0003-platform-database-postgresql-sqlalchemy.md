# ADR-0003: Platform database — PostgreSQL with SQLAlchemy 2.0 (async) and Alembic

- Status: Accepted
- Date: 2026-11-11

## Context

The platform stores relational data: users, auth sessions, projects,
conversations, messages, jobs (agent runs), run events, project files and
integration credentials. It needs transactions, foreign keys, unique
constraints and a reliable migration history. An earlier exploration
(Nov 6, 2026) used MongoDB; the developer comes from Prisma (JS).

## Decision

- PostgreSQL is the platform's single database (pgvector may be added later
  for memory).
- SQLAlchemy 2.0 with typed `Mapped[]` models and async sessions (asyncpg).
- Alembic for every platform schema change; no manual schema edits.
- Conventions:
  - UUID primary keys generated by the application.
  - `timestamptz` columns, stored in UTC.
  - Explicit naming convention for constraints and indexes (stable Alembic diffs).
- Session and transaction rules:
  - One `AsyncSession` per request or per background task; never shared
    across concurrent tasks.
  - Transactions are short. No transaction is held open while Claude generates
    code, E2B installs packages, or any other slow external call runs:
    commit before, do the slow work, persist results in a new short
    transaction.
- This database belongs to the PLATFORM only. Generated apps never use it, and
  platform migrations (Alembic) are never mixed with generated-app migrations
  (see ADR-0005).

## Alternatives considered

- MongoDB (explored Nov 6): our data is relational; we need joins, foreign
  keys and multi-row transactions.
- Prisma Client Python: repository archived (April 2025), unmaintained.
- SQLModel: convenient for simple CRUD, but complex cases still require
  SQLAlchemy directly; adds a layer without removing the need to learn it.
- Tortoise ORM / Piccolo: smaller ecosystems, weaker migration tooling.

## Consequences

- Mature, well-maintained stack with strong async support and autogenerated
  migrations.
- One database to operate, back up and reason about.

* Steeper learning curve than Prisma for a JS developer.
* Long-running work must be structured around short transactions.
